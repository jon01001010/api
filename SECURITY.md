# PocketAgent security rules

To report a security problem privately, see [.github/SECURITY.md](.github/SECURITY.md). Fixes so far: [docs/security-changelog.md](docs/security-changelog.md). What is kept where, for users: [docs/privacy.md](docs/privacy.md).

These rules keep the app safe as it grows: new tools, downloaded assistants and mods. Each rule has a test in `src/__tests__/securityRules.test.ts` (and the Windows app's native side has Rust tests in `src-tauri`), which fails if a change weakens it. **If one of those tests fails, don't just update the test.** Read the rule, decide on purpose, and update this file in the same change.

Audit of 2026-11-06: every place where untrusted input (model output, downloaded assistants, web pages, links from other apps, stored data) meets something powerful was checked. Findings and fixes are in `TODO.md` ("Off means off", "HTML preview lock").

## 1. Tools run in two places only

- Only the chat loop (`src/services/agent/AgentRunner.ts`) and a shortcut run (`src/services/talents/customTools.ts`) call a tool. A loop plan's tool step goes through the chat loop's own gate (`runToolCall` in `AgentRunner.ts`), never to a tool directly.
- The chat loop refuses any tool that is not on the allowed list for that turn, even if the model names it.
- Only a shortcut run skips the per-step question, and only after the user approved the whole shortcut, with every step shown. Each step's tool must be switched on in the Toolbox: a shortcut with a step whose tool is off is refused before the approval ("… is switched off in the Toolbox. Nothing was done."), and a tool switched off while it runs stops it at that step. A chain of phone actions (`phone_actions_chain`, `src/services/talents/PhoneActionChain.ts`) is not a shortcut: it shows every step first, then each step still asks before it runs.

## 2. Off unless the user turns it on

- Every tool starts switched off. Missing or broken settings mean no tools (fail closed).
- An assistant, including a downloaded one, may add only `calculate`, `datetime` and `render_html` by itself. Every other tool needs its Toolbox switch.
- Tools the model saves, and tools imported later (QR, file, mods), are saved switched off and re-checked every time they load.
- A shared tool (Toolbox → Scan QR, Paste a code, or a shared file; `src/services/talents/toolQr.ts`, `toolImport.ts`) is data only: the code is unpacked with size caps (32 KB of code, 16 KB of tool after unpacking, stopped early so a small code can't unpack into a huge one), only the fields a tool has are kept, then it goes through the same checks as `tool_save`. Its full definition (every step and fill-in) is shown before Install, it is installed switched off, and a name already in use is never replaced (the user picks another name). Nothing from a code runs. A `PA1:P:` code read there goes to the usual pairing (it asks first), a `PA1:L:` code to the shared-loop review (below); any other code is refused.
- Memory search (Toolbox → What the model sees → Memory) sends all notes unless the user picks "Only notes that match". Searching earlier chats is a separate switch, off by default: only the user's own messages typed on this device (a message that came from another device in a mirrored chat carries a local mark, `mirroredFrom`, and is skipped, so a paired device can't plant "your own words"; the mark never travels), never from the current chat, a deleted chat or one with a deletion tombstone, at most 3 short pieces, wrapped as untrusted text (nonce markers, like web pages) so they are information, never instructions. They go only to the model the user is chatting with.
- Phone actions ask every time. Nothing calls, sends or pays by itself. A chain of them (at most 5, phone actions only, each switched on) asks before every step; a no, a failure or Stop ends it.
- Ready-made loops (`src/services/loops`) never run by themselves: when one is due the app asks (Skip / Later / Run now), and a run is an ordinary message in the loop's own chat, under every rule above. A loop is data (a shipped prompt with the user's blanks as plain text, a schedule and limits); the model has no tool to start, change or reschedule one. Hard limits: 60 runs, 60 days, 10 loops. Only the user edits a running loop (Edit on its card; the same limits, days counted from its start, runs never below those done). Before Start a dry run shows the exact first message without sending anything. Guards that only ever hold a loop back: a phone battery guard (not met → it waits, no question) and a no-progress stop (two runs in a row with the same next steps or reply → paused, with the reason on the card; only the user resumes). A shared loop (`PA1:L:` code, `src/services/loops/loopShare.ts`) is data like a shared tool: unpacked with the same size caps (12 KB after unpacking, stopped early), only its definition is kept (name, goal and steps or prompt, schedule, limits, battery guard; never someone's runs, log or chat), built with the same hard limits (clamped), shown in full with its dry run, and installed paused and not started: it can't be run until the user presses Start on its card. The log records which tools each run's reply called (plain names only).
- A loop can be a **plan** (steps the app runs; `src/services/loops/plan.ts`, `planRunner.ts`, `planStore.ts`): data, never code. The runner knows a fixed list of step kinds (ask the model, use a tool, ask the user, wait, check, repeat, notify, save); a draft from the model, a saved copy and the editor all go through one strict validator (unknown kinds, unknown fields and any tool that isn't built-in are dropped with a note; `tool_save` / `tool_delete` and custom tools are never allowed; text and numbers capped; at most 20 steps, repeats at most 10 times). Results of earlier steps are filled in as plain text, in one pass. A tool step runs through the chat loop's gate with only the built-in tools switched on in the Toolbox at that moment, and the tool's own "Allow?" still asks; save steps use the memory / file tools and their approval. Model steps get one completion with no tools. A run starts only after the user's Run now (the usual "due" question), and an "ask me" step waits for one of its buttons. Guards per run, on by default and raised only by the user (capped): 50 steps, 10 minutes of working time, 10 model calls, 10 tool calls; plus a time limit per step, a no-progress stop (the same step with the same result twice) and a runaway stop: one unfinished plan run at a time, a run uses a copy of its plan, the runner has no way to change a plan, a schedule or a tool switch, and a plan's steps can't be edited while its run is unfinished. A guard hit pauses the run and says which and why; stop / continue once / raise the limit is the user's choice and is logged. A run is saved after each step; after the app restarts it pauses, and a step that was mid-flight is asked about (run again / skip / stop), never re-run by itself. The dry run shows each step and every question without calling the model or any tool. Each edit is a new version (the last 10 kept); going back saves the old one as the newest. Plan loops can't be shared yet.

## 3. The HTML preview is a closed box

- There is one WebView, and it has no bridge into the app (`onMessage` is never set) and no file access. It can't navigate, open pop-ups or keep anything between previews.
- Every page starts with a CSP that blocks all network use, then a guard script that removes WebRTC (which a CSP can't block), blocks `window.open` and removes frames. Frame tags in the page text are renamed before the page is built.
- A saved `.html` file opened in another browser is outside this box.
- On the desktop (Windows / Linux app) the box is a frame instead of a WebView: the native side serves the page from its own address (`pa-preview`) with the same no-network policy plus `sandbox allow-scripts`, and the frame is sandboxed to scripts only (no origin, pop-ups, forms, downloads or storage). It gets no bridge: Tauri gives its secret call key to the app's own page only. The app window allows frames from `pa-preview` only, so a preview can't navigate itself anywhere else.

## 4. Data is never run as code

- No `eval` or `new Function` anywhere in the app, except inside the preview sandbox.
- Values are put into data, never into text that is then parsed. For example, shortcut fill-ins replace text inside a value and can't add fields.
- Each phone action builds the Android request from its own named fields. Model arguments are never passed through as they are.
- File names must match a strict pattern: no folders and no `..`.

## 5. The phone side stays small

- The app asks for a fixed list of Android permissions. Adding one means updating the test and this file.
- Only the main screen can be opened by other apps. Links from outside only fill in the chat box or offer a model download; they never send or run anything.
- Ready-made loops: "loop due" notifications use inexact alarms (no exact-alarm or boot permission) and a receiver other apps can't reach (`LoopAlarmsModule.kt`, not exported). Tapping one only opens the app, which asks Run now / Later / Skip, and only for a loop that is really due; nothing runs without that tap.
- The local API listens on the phone itself (127.0.0.1) only. It checks the Host header and a random password, compared in constant time, and accepts text only, with no tools.
- Home link, phone side (`native/homelink`, `HomeLinkModule.kt`): pairing starts only from the PC's QR code (`PA1:P:` tag; anything else is refused), the phone asks first and the PC asks its user too. Removal notices (device circle, rule 6) travel with the status round trip; the phone keeps their state in an owner-only file next to its key. The phone's tunnel to the PC listens on 127.0.0.1 only and turns away anything else; it reaches only the PC's model server, and needs that server's password. A picture asked of the PC (rule 6) comes back as at most 8 MB of PNG, saved only in the app's own cache folder. The PC's tools ("On your PC", rule 6: the read-only ones and, since stage 2, open / print / media keys / clipboard, and since stage 3 a command, which ask on the PC every time) send only the tool's name, a random id for the chat (never the chat itself), a file name, a media key (from a fixed list, checked on the phone and again on the PC) and a command (checked on the PC by its own rule); the answer is at most 2 MB of JSON, and its text reaches the model wrapped as untrusted. The phone's own key stays in the app's no-backup folder (never in a cloud backup). No new Android permission.
- Home PC PIN (`src/services/homeLink/homePcLock.ts`, set per PC in its server sheet; off by default; the same on a second PC used as the client): while on, every home link request (status, start model, tunnel, keeping in step, questions and answers, pictures, the PC's tools) is refused in one place (`homeLink.ts`, before the native module) until the PIN is entered; what the user does (a chat message, Load, Sync now, a picture, answering a question) opens the PIN window first, and what the app does by itself (model lists, question polling, mirroring) is just refused. It is asked again after the app was in the background for more than the chosen minutes (default 5) and after every restart; the local tunnel is closed then, so an open port can't be used either. Only a salted PBKDF2-HMAC-SHA256 hash is kept (30,000 rounds, plain JavaScript in `pinHash.ts`, checked against the standard test vectors; 100,000 would take 3-6 s on a phone without a JIT), in the app's key store with servers' API keys (Android Keystore; Windows Credential Manager on the desktop), never the PIN. 5 wrong tries, then a 5-minute wait that doubles each further 5 (at most a day); the count is written before each check and kept in the key store, so a restart doesn't reset it. The wait left is kept (not only its end time) and counts down only by time the app measured itself: the smaller of the wall clock's and a monotonic clock's (`performance.now`) time while the app runs, so setting the date forward or back, or restarting the app, doesn't shorten it (the wait counts down while PocketAgent is open, and the message says so). Changing it or turning it off needs the current PIN. Forgot it: the only way back is to pair again, which the PC must approve (pairing clears the old PIN; removing the PC from the device clears it too, and gives nothing without a new pairing). Fingerprint (Android only, optional, the PIN still works): a random secret in the Keystore under a key that only opens after Android's own fingerprint check (react-native-keychain's `BIOMETRY_CURRENT_SET`, androidx.biometric, already in the app with its `USE_BIOMETRIC` permission; no Google Play services); adding a fingerprint to the phone invalidates it. **What it doesn't protect:** what is already on the phone (chats, mirrored chats, memory, pictures from the PC) and the app itself; someone who copies the key store off a rooted phone can search a 4-8 digit PIN offline (the rounds slow that, they can't stop it); and a phone that is unlocked and in use within the minutes chosen. Removing the phone on the PC stays the fix for a lost phone.

## 6. The Windows app opens doors only on purpose, and asks

The Windows app (`src-tauri`, branch `windows`) is the same app in Windows' web view. Rule: broad access, never automatic.

- The window has no internet access of its own (its content security policy). Its only frames are HTML previews from `pa-preview` (rule 3).
- Network, files, keys, previews and the model server are commands on the native side, each listed in `src-tauri/build.rs` and allowed in `src-tauri/capabilities/default.json`. Nothing else is allowed.
- Every native command runs off the window's main thread (`async`), so a slow one can't freeze the window.
- Files: the app's own folder (AppData) needs no prompt. Anywhere else, every read, write, list or delete shows an "Allow?" dialog **from the native side**, so the web screens can't skip it. `..` is refused everywhere.
- Models: the bundled llama.cpp server (pinned release, checksum checked) listens on this PC only with a random password. Running a model file from outside the app folder asks first: Allow once, Always allow this file, or Don't allow (closing the dialog is Don't allow). "Always" is only ever set by that button, and is kept in Windows Credential Manager under names the screens can't write (their key command always adds "PocketAgent:"). It covers that exact file (path, size, last-changed time): a changed or replaced file is asked about again. A model the app downloaded itself is named by its own path (`/pocketagent/…`, inside the app folder) and runs without a question; its vision part (`--mmproj`) is only ever a file the app downloaded. LoRA adapters (small .gguf style add-ons for a model) follow the same rules, stricter: one is only ever a file in the app's own folder (added through the app's own file import: the phone's file picker, or the desktop's native "Add a file" dialog, which copies it in), never a link, never from outside without that import and never a path from a paired device (a phone starting the PC's last model gets the adapter the PC user chose, nothing it names). It goes to the model server as `--lora-scaled` (strength 0–1); the server keeps running in its own folder, never in the app's data folder, because llama.cpp also loads backend DLLs from the folder it runs in. On the phone llama.rn applies it in place; one that doesn't fit leaves the plain model.
- Keys: Windows Credential Manager, never plain files. In a plain browser, saving keys is not available.
- HTML previews give the page a storage that lives only while it is open (`localStorage` / `sessionStorage` in memory; the real one throws in the no-origin preview and stopped pages' scripts). Nothing is saved or shared with the app.
- Opening things in the PC's own apps (`src-tauri/src/open.rs`, the desktop version of the phone's actions): only a web page (same check as the network door), an e-mail draft (`mailto:` with to / cc / bcc / subject / body only, never attachments; the user presses send) or a fixed list of Windows settings pages (`ms-settings:`; nothing is changed). Each asks in a native dialog showing exactly what opens; no shell: Windows' own handler (`ShellExecuteW`), on Linux `xdg-open` with the address as one argument. Calls, texts, the camera, music and other programs are not opened from the PC.
- The PC's own tools (`src-tauri/src/pc.rs`, desktop app only, each off until switched on): `pc_info` reads the hardware (read only). `run_command` shows the whole command in a native dialog **every time** (Allow / Don't allow; never "always"), with its number of lines and characters; a command with carriage returns, control characters or invisible format characters (bidi overrides, zero-width spaces, …), or more than 20 lines, is refused, so the dialog can't show something other than what runs or push a tail off the screen. It runs it in the workspace folder, stops it after 60 s and returns its output (cut). It can do anything the user can, which is why it asks each time. A paired device's `pc_run_command` (stage 3, below) goes through this very same function (`pc::run_checked_command`; the PC's own command calls it with no device), so the same checks, dialog, folder, time limit and cap apply. `open_file` opens a workspace file in its app after asking; documents, pictures, text and media only, never programs or scripts (opening those would run them).
- More PC tools (`src-tauri/src/pc_extra.rs`, desktop only): `clipboard_read` shows the clipboard's text in a native dialog before the model gets it; `media_control` presses only media keys (play / pause, next, previous, stop, volume, mute) after a native dialog; `print_file` prints a workspace document or picture after a native dialog (never programs or scripts). Screenshots are the user's "Screenshot" button (where the phone has Camera): a native dialog first, DesktopAgent hides itself while it is taken, and the picture is attached for the user to see; it reaches the model only if they send it. System notifications show text only. The quick-chat key (Ctrl+Shift+Space) only brings DesktopAgent to the front and is registered only when switched on in Settings. The tray icon opens or quits the app.
- Pictures (`src-tauri/src/image_gen.rs`, tool `image_generate`, desktop only, off until switched on): made on this PC by stable-diffusion.cpp's one-shot `sd-cli` (pinned release, checksum checked on Windows; built from the same pinned commit on Linux x64; none on ARM Linux). Never `sd-server`, which has no password: it is removed from the bundle. `sd-cli` opens no port and fetches nothing; it runs only the model files the app downloaded itself into its own folder (`Documents/image-models/<set>`, names from the model list `src/services/imageGen/imageModels.json`; the screens name a set, never a path). The picture is written to the workspace's `images` folder (the app's own folder, so no dialog); the prompt is shown in the chat as the tool call. Caps: prompt at most 1000 characters with no control or invisible characters, sizes 512 / 768 / 1024 only, at most 30 steps, one picture at a time, stopped after 10 minutes, and the chat's Stop kills it. The chat shows only pictures from that `images` folder; Save a copy is the usual native Save dialog. A small word check on the native side refuses clearly illegal prompts (sexual content involving minors) before anything runs. **It is a basic filter, not a guarantee**: it only sees words (other languages, misspellings and paraphrases get through), and the engine and models have no content filter of their own. The model list holds only models whose licence allows commercial use (FLUX.2 klein 4B: Apache-2.0; SD 1.5: OpenRAIL-M, whose use rules are shown before download); the licence note is shown the first time. A paired device can ask for a picture only as described under "Pictures for paired devices" below.
- Pictures for paired devices (link request "picture", `src-tauri/src/link.rs`; phone tool `image_generate`, `src/services/talents/PcPictureEngine.ts`): off on both sides by default. The PC's switch "Let paired devices make pictures on this PC" (kept in the credential store, out of the screens' reach) **and** that device's own "Pictures" switch in the PC's list of paired devices (off for each device, including those paired before, and again after pairing anew; switching it on asks in the PC's own native dialog, which no device can answer, and is recorded in the pairing history) must both be on, or the device is refused ("Making pictures for paired devices is off on the PC" / "This device may not make pictures on this PC; allow it on the PC"); on the phone the tool is off until switched on in Toolbox, like every tool. The device sends a prompt and, at most, sizes and steps: never a model, a path or a seed (anything else in the request is ignored); the PC uses its own first downloaded picture set and runs exactly the same checked maker as its own tool (`image_gen::make`: the same caps, the same word check, the same one-picture-at-a-time slot shared with the PC's own pictures, the same 10-minute limit). The PC shows a notification when a device starts one ("<device> is making a picture: <prompt…>"), and a copy stays in its workspace `images` folder. The answer is a JSON line, then the PNG (at most 8 MB, checked to be a PNG on both sides). If the device goes away or is removed meanwhile, its picture is stopped. An error sent to the device (sd-cli's last lines name model and home folders) has this PC's folders replaced by `<home>`, `<app folder>`, `<workspace>`, `<temp>`, and any other absolute path by `<path>`; so do errors of the PC's tools below. The phone saves it only in its own cache folder (`pc-pictures`, a name the app makes), and the chat shows only pictures from there or the workspace `images` folder; a second PC saves it in its workspace `images` folder.
- The PC's tools for paired devices, stage 1: read only (link request "tool", `src-tauri/src/link.rs`, `pc_files.rs`; phone tools `pc_info`, `pc_workspace_list`, `pc_workspace_read` under Toolbox → "On your PC", `src/services/talents/PcToolsEngine.ts`): off on both sides by default. Only paired devices; then, in this order: the PC's switch "Let paired devices use this PC's tools" (kept in the credential store, out of the screens' reach, and kept across restarts like the pictures switch), that device's own "May read" switch in the PC's list of paired devices (off for each device, including those paired before, and again after pairing anew; switching it on asks in the PC's own native dialog, which no device can answer, and is recorded in the pairing history), the tool on a fixed list of three (`pc_info`, `workspace_list`, `workspace_read`; anything else is refused), then its arguments: a random chat id from the device (16-64 letters, digits, `-`, `_`) and, for a read, one workspace file name (the screens' own name rule: letters, digits, `.`, `_`, `-`, spaces, starting with a letter or digit, at most 120 characters; never a folder, a path, `..`, a hidden name, a Windows device name such as `CON` or `COM1`, `desktop.ini` / `Thumbs.db`), passed through the same check as the PC's own open and print (`pc::workspace_file`). Only plain files directly in the workspace folder: never a folder, a link to somewhere else, or (on Windows) a hidden or system file. Text files (the screens' list of text kinds) and documents (through the PC's own reader, `docs::read_document`, with its 64 MB cap) only, but never a PDF for a device (a damaged PDF can overflow the PDF reader's stack, which would stop the app; the device is told to open it on the PC); a device's document is read in its own thread with a 64 MB stack, one at a time, within 30 seconds (`pc_files::read_for_device`); at most 256 KB of text comes back (cut beyond, said so), the whole answer at most 2 MB. `pc_info` is the PC's own function and asks nothing, as on the PC. Listing or reading the workspace asks on the PC **once per chat** (a native "Allow?" naming the device: "… asks to read files in your workspace for this chat"; a device that may answer this PC's questions may answer it, the asking one too, as for any question); the yes is kept in memory only, per device and chat id, for 12 hours at most (asked again after a restart), and for at most 3 chats of one device at once (the chat id is the device's own choice: a new one ends that device's oldest; the question says how many it already has), and is forgotten when the PC's switch goes off, the device's "May read" goes off, or the device is removed; the switches are checked again after the answer. Each file read shows a PC notification with the count ("Pixel 8 read budget.xlsx from the workspace (2 of at most 3 chats allowed to read)"), and every use (PC info, list, read) is logged with the device's name in the same log as answers given on devices (one line, escaped, out of the screens' file space). On the device: each tool is off until switched on in Toolbox, the Home PC PIN is asked first, and the PC's answer reaches the model wrapped as untrusted (a file can carry instructions).
- The PC's tools for paired devices, stage 2: actions that already ask (link request "tool"; phone tools `pc_open`, `pc_print`, `pc_media`, `pc_clipboard_read`, the same names on the PC's list, under Toolbox → "On your PC"): off on both sides by default. The checks keep stage 1's order: paired → the PC's tools switch → the device's flag for that tool → the fixed list → the arguments. The flag for these four is the device's own **"May act"** (separate from "May read"; off for each device, including those paired before, and again after pairing anew; switching it on asks in the PC's own native dialog, which no device can answer, and is recorded in the pairing history as `may-act`); "May read" alone can't act and "May act" alone can't read. The fixed list grows by exactly these four (`ACT_TOOLS`). Arguments: the chat id as in stage 1, one workspace file name (the same name rule) for open and print, one key from the PC's own media key list for `pc_media`, nothing for the clipboard. Each runs **the very same function as the PC's own tool** (`pc::open_file`, `pc_extra::print_workspace_file`, `press_media_key`, `read_clipboard`; the PC's own commands only call them with no device): the same checks (open: documents, pictures, text and media only, never programs or scripts; print: documents, pictures and text; workspace files only) and the same plain native "Allow?" **every time** (Allow or Don't allow, never "always"), whose first line names the device ("“Pixel 8” asks to open this workspace file in its app on this PC"). A device that may answer this PC's questions may answer it, the asking one too (owner decision 1c); after the answer the PC checks again that its tools switch is on and the device may still act (`approval::ask_for`). The clipboard question shows the text, as for the PC's own tool; the text is never written to the answers log, whoever asked (the log keeps the first line with the device's name and the length), nor shown in the "answered on a device" notification. Each action shows a PC notification ("Pixel 8 opened report.docx on this PC"; the clipboard by its length only) and is logged with the device's name. On the device: each tool off until switched on in Toolbox, the Home PC PIN first, a media key checked against the list before anything is sent, and the clipboard's text reaches the model wrapped as untrusted.
- The PC's tools for paired devices, stage 3: commands (link request "tool"; phone tool `pc_run_command`, the same name on the PC's list, under Toolbox → "On your PC"): off on both sides by default. The checks keep the same order: paired → the PC's tools switch → the device's flag for that tool → the fixed list → the arguments. Its flag is the device's own **"May run commands"** (`may_command`; separate from "May read" and "May act", neither of which can run a command, and it can't read or act; off for each device, including those paired before, and again after pairing anew; switching it on asks in the PC's own native dialog, which no device can answer, with a strong warning that the device "can run anything you can on this PC, after you allow each command", and is recorded in the pairing history as `may-command`). The fixed list grows by exactly this one (`COMMAND_TOOLS`). Arguments: the chat id as in stage 1 and one command, which must pass the PC's own `check_command` (no carriage returns, control or invisible / bidi characters, at most 20 lines and 2000 characters). It runs **the very same function as the PC's own `run_command`** (`pc::run_checked_command`): the whole command in the native "Allow?" **every time** (Allow or Don't allow, never "always"), with its line and character counts, its first line naming the device ("“Pixel 8” asks to run this command on your PC …"); the question is never cut, so a device that may answer sees it whole (the asking one too, decision 1c; a phone refuses "Allow once" for a question too long to show whole); after the answer the PC checks again that its tools switch is on and the device may still run commands. It runs in the workspace folder, is stopped after 60 s, and its output is capped at 32 KB. The output sent back has this PC's own folders and any other absolute path taken out (line by line, `link::output_for_device`, the same rule as for errors) and is capped again. Each command shows a PC notification (the device and the command's first 60 characters, escaped) and the whole command is written to the answers log (one line, escaped; commands are not private like the clipboard). On the device: off until switched on in Toolbox, the Home PC PIN first, the command's size checked before anything is sent, and the whole answer (exit code and output) reaches the model wrapped as untrusted.
- Documents (`src-tauri/src/docs.rs`): Word, Excel, PowerPoint, OpenDocument and PDF files in the workspace are read as text on the PC (size and "zip bomb" limits; a broken PDF can't close the app by a panic; a PDF is never read for a paired device, above). Nothing is uploaded; never files outside the app's folder.
- Files in and out (`src-tauri/src/transfer.rs`): only through the user's own choice in a native file dialog (Add a file: a copy goes into the app's folder; Save as: a copy of an app file goes where the user picks). The model can't do either.
- Network from the native side is http and https only, never the app's own internal addresses (`*.localhost`: the native bridge `ipc.localhost`, the app, previews), and never with the bridge's per-start key (`Tauri-Invoke-Key`). The page's network layer leaves those addresses alone too (`web/tauriNet.js`). Before 2026-11-09 the page sent the bridge's own Windows address through the native side, so each native call called itself until the page gave up (the 40 s Windows start); the requests that then reached the native side were for `ipc.localhost`, a name Windows does not resolve, so nothing left the PC. Both sides now refuse it, with tests.
- Publishing test builds uses the owner's own token (repository secret `RELEASE_TOKEN`: this repository only, Contents + Workflows, with an expiry), only in the "Publish pre-release" steps, which run nothing but `gh`. A test fails if it shows up anywhere else. Forks never receive it.
- Every published build comes with a `SHA256SUMS` file (a test checks each publish step). The published APK is the **release** variant (`prodRelease`): not debuggable (a debuggable app lets anyone with the unlocked phone and a USB cable read its private files, such as the home link key, with `adb run-as`) and without React Native's dev support (`USE_DEV_SUPPORT` false: it never loads JavaScript from a "Metro" server, which another app on the phone could pretend to be); its Hermes bundle is built in. The workflow checks this (`aapt2 dump badging` / the manifest: no `debuggable`; the bundle is Hermes bytecode) after the build and again before and after signing, and fails otherwise. The APK is built in one job and signed in another (`sign`): a fresh runner with no repository rights that checks nothing out and runs nothing from the build (npm install scripts, Gradle plugins, the NDK build ran elsewhere), only GitHub's artifact download / upload and the runner's own `apksigner` from pinned build-tools. It signs with our own release key from repository secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`), in that one step only, the key written to the runner's temporary folder and removed after, and verifies the signature; without them the APK keeps React Native's public debug key (Gradle signs the release variant with it when no release keystore is set, so test builds still install over each other) and the release notes say so. Only then does the release job publish it with its checksum. Windows installers are not code-signed yet.
- Build caches: a pinned download (llama.cpp, stable-diffusion.cpp on Windows, llama.rn's native libraries) restored from the Actions cache is checked against its pinned SHA-256 like a fresh download. The Linux `sd-cli`, built from the pinned commit, has its SHA-256 recorded in its cache key when it is built; a restored copy must match it or the build fails. (This catches a copy changed after it was saved; it can't vouch for what was built, which is why the build checks the pinned commit.)
- Keeping in step (`src/services/sync`, link request "sync"): the system prompt, memory notes, your own assistants (not their chosen model or picture) and custom tools travel between paired devices only, over the encrypted link, only when switched on **on both** (the PC's "Let paired devices keep … in step", and the device's switch for that PC); off by default. The newer edit wins item by item; empty never wins over real text; the replaced text is kept in history on that device (memory snapshots; the last 10 of the others). Times from the other device count as at most 5 minutes ahead, and what is applied is stored with this device's own time, so a clock far ahead (or a forged time) can't make an edit win forever. Your own assistants are merged one by one (each with when it last changed; matched by id, then by name): deleting one leaves a tombstone (id, name, time; the last 200, 90 days at most; malformed entries and times more than 5 minutes ahead are ignored, edit times are clamped the same way) that removes the other device's copy only if that copy hasn't changed since; the removed assistant is kept 30 days under "Recently deleted" on that device (with its picture and model choice, local storage) and can be restored; more than 5 deletions in one sync are not applied without asking. Downloaded (store) assistants are never matched, rewritten or deleted by a sync. Loops (`loopSync.ts`) are merged one by one the same way (matched by id only; tombstones of stopped loops, edit times clamped, 30 days under "Loops recently deleted", restorable, more than 5 deletions asked first), but only a loop's **definition** travels, exactly the fields a shared loop code carries (`loopShare.ts`: name, goal and steps or prompt, how often, time, run and day limits, battery guard), cleaned and held to the same hard limits as a shared code (an entry over 12 KB or one that wouldn't install is dropped): never its runs, log, chat id, next time, paused state, progress fingerprints or battery readings. A loop from another device is installed **paused and not started** (the sync result says "2 loops from the PC; start them under Toolbox → Loops"), so nothing runs on two devices unless the user presses Start on each; a changed definition updates a loop here and keeps its own runs, chat and schedule state; a running loop is paused ("Changed on <device>; press Resume to run the new version"), so another device can't quietly change what runs here; one whose new limits no longer fit what ran here is set back to not started. A device with 10 loops takes no more (and says so). A "Recently deleted" list (assistants, loops, chats) that can't be read is never taken as empty and saved over: nothing is removed then (`keptStore.ts`); sizes are counted in UTF-8 bytes. Toolbox switches are **not** kept in step: a loop's run uses the Toolbox of the device it runs on, and each device asks for its own actions. Custom tools arrive through the same checks as a saved tool and stay off until switched on on that device (Toolbox): a tool the sync adds, changes or removes is switched off before the new list is saved, and deleting a tool always switches its name off. Every change to the Toolbox switches runs one at a time and changes only the names switched (against the list as stored then), so a Toolbox left open during a sync can't write its older list back and turn a synced tool on again; an open Toolbox reloads when the switches change. On the PC, "Kept in step" notices show one at a time (later ones together after). Each side is size-capped (4 MB). A paired device can change this PC's system prompt and memory this way, which is why it is a separate switch and the PC says when something changed.
- Mirrored chats (`src/services/sync/chatSync.ts`, `chatDeletes.ts`): chats travel only when mirroring is switched on on both (separate from keeping in step, as chats are more private), with keeping in step on too, over the same encrypted link and size cap. Only newer or missing chats move; chats keep their ids; times count as at most 5 minutes ahead. Pictures stay on the device they were taken on: a mirrored message keeps only known fields and known metadata (text, the reply's steps as text, timings and similar), never picture paths, audio files, an author id or anything naming a file; only messages from the user, the assistant or a summary, of the kinds the app saves, are taken. A copy that drops or changes messages a device has keeps that device's earlier version 30 days under "Recently deleted" (restorable; up to 3 versions per chat, the first one kept never dropped for a later one, so syncs in a row can't push the original out; with no room for it, or a list that can't be read, the copy is not taken). The list is stored in parts of at most 900 KB (UTF-8 bytes, well under Android's 2 MB read window; 1.5 MB in all), and a list that can't be read is never saved over. When sending to a model server the app never passes on a web address as a picture and reads only pictures in its own folder. Deleting a chat travels as a tombstone (chat id and time only; the last 500, 90 days at most; malformed ids and times more than 5 minutes ahead are ignored): it removes the other device's copy only if that copy has not changed since (a newer edit wins). A chat removed because of another device's deletion is kept 30 days under "Recently deleted" on that device (full copy, local storage, its own size room; a chat that doesn't fit isn't removed) and can be restored; more than 20 deletions in one sync are not applied without asking; the sync result says how many were deleted.
- The PC asks, a device can answer (`src-tauri/src/remote_ask.rs`, `approval.rs`, link requests "questions" and "answer"): only while switched on **on both** (the PC's switch is off at every start until the saved choice turns it on). A paired device sees the PC's "Allow?" questions word for word (direction and invisible characters shown as markers such as ⟦U+202E⟧: the same set as the PC's `remote_ask::hidden_char`, soft hyphen and tag characters included; a test pins the two lists) and can answer yes or no to one question by its id, within 2 minutes; a question too long to show whole shows its start and end (never cut at the end) and can only be refused on the device; the first answer (device or PC) wins; a device's yes is always "allow once", never "always"; pairing a new device is asked on the PC only. Only the devices allowed one by one on the PC ("May answer" in its list of paired devices; off for each device, including those paired before this choice existed, and again after pairing anew) get the questions or may answer; any other paired device is refused ("This device may not answer this PC's questions; allow it on the PC"). Allowing a device is asked in the PC's own native dialog, which no device can answer, and is recorded in the pairing history the paired devices see; stopping it asks nothing. Each device answer is logged on the PC (`link/answers.log`: the device's name, its answer and the whole question on one line, escaped, up to 4000 characters; the clipboard's text is never logged, only "clipboard (N characters, not logged)"; past 1 MB the log moves to `answers.log.1`, so about 2 MB are kept), in a folder the screens' file commands can't reach without asking (the settings folder on Linux, local AppData on Windows). When a device answers, the PC user gets a notification at once ("<device> allowed: …"); the PC's own dialog can't be closed from the native side, so whatever is pressed there afterwards changes nothing and a note says "This was already answered on <device>". This means a paired device can allow what the PC would ask about, which is why it is its own switch, off by default.
- PC to PC (`src-tauri/src/link_client.rs`): a second PC can be the other end of a home link, with the phone's own link library unchanged (127.0.0.1 only, the PC's one-time code only). **Keys (device circle stage 1, 2026-11-15): one key per PC.** A PC is the same key as a device of another PC as it is to its own devices: its link key, on the very same endpoint (`link::device_endpoint`, `Phone::with_endpoint`; never a second endpoint with that key, which would push the first off the relay). While the link is switched off that endpoint offers no protocol and refuses every incoming connection (so being a device never lets anyone in). New installs use one key from the start. A PC that already had its own device key ("client key") keeps using it, nothing moves by itself (owner decision 8b): "Use one key for this PC" (Settings, after a question naming the PCs it uses) switches it, and its pairings as a device are then made again by hand, each asked on the other PC as always; the old key is kept in the store, unused. Keys are kept as before, out of the screens' file space (Windows Credential Manager; on Linux an owner-only file in the settings folder); a key file from before 2026-11-15 is moved there, so pairing is kept. The phone's key file is owner-only (0600), in the no-backup folder. "Your devices" (Settings) lists every device paired either way, with what this device gave each (per pair) and when it was paired; it only reads, gives no right, and removing there is what removing did before, here at once, and (stage 2) it tells the other devices, below. The code is pasted instead of scanned ("Copy the code" on the main PC); the main PC still asks before pairing, and the second PC is listed and removable there like a phone.
- Home link ("Use this PC's model from your phone", `src-tauri/src/link.rs`): off until the user switches it on. Devices dial each other by public key (iroh); the connection is encrypted from the PC to the phone, and a relay (used when no direct path is found) passes it on without being able to read it. Pairing: a QR code with the PC's key and a one-time code (10 minutes; used up by the right code or the 4th wrong one, wrong tries counted across all device keys, compared in constant time), then a native "Pair with the phone …?" dialog; only then is the phone's key saved. The model server's password is passed by environment (`LLAMA_API_KEY`), never on its command line (which any program on the PC can read). Through the link, every request is one stream, read whole and checked before anything reaches the model server: it must be one of the model server's own requests (health, props, models, chat / completions) with the model's current password, with a plain `Content-Length` body (no `Transfer-Encoding`, at most 16 MB, no folded or broken headers) and nothing after it (a second, pipelined request is refused); the model server gets it with `Connection: close`, so it answers once and closes, and the phone closes its local connection then, so the next request is checked the same way. Anything else gets 403, so another app on the phone that finds the phone's local port gets nothing, and `/slots` and other endpoints can't be reached by riding along. In chat and completion requests, pictures, sound and video must be inline (`data:`): an address (`http://…`) is refused, because the model server would fetch it from inside the PC's home network. The model server runs with `--no-slots` (its `/slots` would hand out the last conversation), and `/metrics`, `POST /props` and slot saving stay off. A paired phone can do exactly three things on its own (plus answering this PC's questions, asking for pictures and using this PC's read-only tools, each only while allowed for that device, above): ask whether a model is running, start the model this PC last ran (the PC picks it, the phone names nothing; never one that would need an "Allow?" on the PC: a file outside the app folder that isn't "always allowed" is refused, since nobody may be at the PC), and pass HTTP requests to this PC's own model server on 127.0.0.1. Nothing else is reachable (no other files, tools or ports). Paired phones and the link key live in the credential store under names the screens can't write. Remove a phone and it is shut out at once: its open connections (a model request, a sync) are closed, and for an hour it can't ask to pair again. A device that is already paired or was removed lately can't use up a pairing code; a wrong code from a new device key counts as one of the code's 3 wrong tries (a device key is a fresh key anyone can make, so one wrong try doesn't burn the code). A device must send its request line within 10 seconds, and runs one sync at a time. Pairing history: every code made, phone paired and phone removed is recorded on the PC and sent to the paired phones with each status, so a code made while you're away shows up on your phone ("Pairing activity on your PC").
- Removal notices (device circle stage 2, `native/homelink/src/circle.rs`, used by the PC's `link.rs` and the phone's library; owner decisions 6a and 9a; a notice about the receiving device is ignored, as the design recommends): "Remove here" in "Your devices" removes the device here at once, as before, and signs a notice with this device's own link key (Ed25519, iroh 1.4.1's `SecretKey::sign`; checked with `PublicKey::verify`, iroh's strict check; no other crypto library). A notice is the removed key, the signer's key, the signer's own number (always rising, never below its clock) and a time, signed after a fixed label (`PA circle remove v1`), so no other signed message can pass for one; anything with more fields is not a notice. It goes to the other paired devices the next time they talk: a PC adds the ones a device doesn't have yet to its status answer (`removals`), and a device (phone or PC) hands its own to each Home PC with a link request `removal` (paired devices only, at most 8 notices) right after the status. A received notice is applied only if it is signed by a device this one trusts (paired either way: the devices that use this PC, and the Home PCs this device uses, as its screens last listed them), its signature holds, its time is at most 5 minutes ahead and at most 30 days old, and its number is above the last one taken from that signer (kept; no replay); one naming this device itself is ignored (a notice can't make a device remove itself), and so are its own coming back. Applying is exactly "Remove here" (`link::forget_here`: record gone, open connections closed at once, no pairing for an hour, reading rights gone, the pairing history says "removed on another of your devices"; a Home PC entry is removed by the screens), without a question, and the user is told (the PC's notification, the phone's alert, naming both devices); the notice is passed on once to the device's other paired devices. A notice can only remove: nothing on its path adds a device, sets a right or asks (a test pins it). The worst a paired device can do with it is remove other devices from the ones that trust it (seen, undone by pairing again). The circle's state (numbers seen, at most 8 notices waiting, news for the screens) is kept with the keys: on the PC in the credential store (in parts, each under the store's size limit), on the phone in an owner-only file in the no-backup folder. The screens can only ask to remove (as they always could) or read what was removed (`link_circle` / the phone's `circle` door: "remove" and "news"; no network). A device that never talks to the others again is not told (remove it there by hand).
- Downloads (models) stream straight to disk through the native side: http/https only, the app's own folder needs no prompt, anywhere else asks; a half-finished download stays a `.part` file and never looks like a model. The native side works out each download's SHA-256; given the expected one, a file that doesn't match is deleted and never renamed into place. Picture models (`imageModels.json`): a file with a `sha256` in the list is checked that way (and again by the screens) and counts as downloaded only once checked; a set marked `verified` with a file lacking its `sha256` is refused; sets not checked yet (`verified: false`, all of them for now, as Hugging Face couldn't be reached when the list was made) download with a "Not verified yet" note.
- The desktop app makes no network calls at start-up (the phone's device-rules fetch from PocketPal's CDN is off on the desktop).
- Tauri's script nonces stay on; its style nonces are off (`dangerousDisableAssetCspModification: ["style-src"]`), because the app's styles are added at run time. Styles can't run code, and the policy stops them loading anything from outside.

## 7. No outside connection the user didn't ask for

Audit 2026-11-09 (every outside address in the code, plus the desktop app's actual traffic in its first minute: none). Phone app audited again in the code 2026-11-15 (every `fetch`, `axios`, `XMLHttpRequest`, WebSocket and native download); the list below is what it found. Its real traffic on a phone is still to be watched once (TODO.md, Pre-release).

- Nothing contacts an outside service on its own: no reports, no analytics, no crash reporting, no Google. `src/config/outside.ts` keeps PocketPal's original senders in the code but off: feedback, content reports, model error reports and shared benchmarks (PocketPal's Firebase / Google App Check, after a google.com probe) are refused before any connection (the error report is copied instead); the device-rules download from cdn.jsdelivr.net at every phone start is off (built-in rules are used). A test pins both off.
- Not built in on Android: Firebase (no project; its JS modules unlinked, its Android libraries commented out), Google Sign-In and Google Play billing (unlinked in `react-native.config.js` since 2026-11-15, so Google's billing library is not in the APK; their JavaScript is replaced by stand-ins that say "not available", `stubs/android`; a test pins it). The PalsHub account code stays but never starts (it needs a Supabase address, which PocketAgent builds don't have; purchases are off: `NO_PURCHASES`).
- New outside connections need this file updated and their switch or consent; reviewed in the security audit before release.

**Every outside address the phone app can contact** (nothing else is in the code):

The desktop app makes no network calls at start-up (rule 6); its outside connections are the same kinds as the phone's (servers you added, model downloads, search tools, the home link).

## For mods (planned)

A mod is data, never code. It lists every tool it uses, its full contents are shown before install, and it installs switched off. It goes through the same checks as a tool the model saves (rule 2).
