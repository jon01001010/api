# PocketAgent security rules

To report a security problem privately, see [.github/SECURITY.md](.github/SECURITY.md). Fixes so far: [docs/security-changelog.md](docs/security-changelog.md). What is kept where, for users: [docs/privacy.md](docs/privacy.md).

These rules keep the app safe as it grows: new tools, downloaded assistants and mods. Each rule has a test in `src/__tests__/securityRules.test.ts` (and the Windows app's native side has Rust tests in `src-tauri`), which fails if a change weakens it. **If one of those tests fails, don't just update the test.** Read the rule, decide on purpose, and update this file in the same change.

Audit of 2026-11-06: every place where untrusted input (model output, downloaded assistants, web pages, links from other apps, stored data) meets something powerful was checked. Findings and fixes are in `TODO.md` ("Off means off", "HTML preview lock").

## 1. Tools run in two places only

- Only the chat loop (`src/services/agent/AgentRunner.ts`) and a shortcut run (`src/services/talents/customTools.ts`) call a tool.
- The chat loop refuses any tool that is not on the allowed list for that turn, even if the model names it.
- Only a shortcut run skips the per-step question, and only after the user approved the whole shortcut, with every step shown. A chain of phone actions (`phone_actions_chain`, `src/services/talents/PhoneActionChain.ts`) is not a shortcut: it shows every step first, then each step still asks before it runs.

## 2. Off unless the user turns it on

- Every tool starts switched off. Missing or broken settings mean no tools (fail closed).
- An assistant, including a downloaded one, may add only `calculate`, `datetime` and `render_html` by itself. Every other tool needs its Toolbox switch.
- Tools the model saves, and tools imported later (QR, file, mods), are saved switched off and re-checked every time they load.
- A shared tool (Toolbox → Scan QR, Paste a code, or a shared file; `src/services/talents/toolQr.ts`, `toolImport.ts`) is data only: the code is unpacked with size caps (32 KB of code, 16 KB of tool after unpacking, stopped early so a small code can't unpack into a huge one), only the fields a tool has are kept, then it goes through the same checks as `tool_save`. Its full definition (every step and fill-in) is shown before Install, it is installed switched off, and a name already in use is never replaced (the user picks another name). Nothing from a code runs. A `PA1:P:` code read there goes to the usual pairing (it asks first), a `PA1:L:` code to the shared-loop review (below); any other code is refused.
- Phone actions ask every time. Nothing calls, sends or pays by itself. A chain of them (at most 5, phone actions only, each switched on) asks before every step; a no, a failure or Stop ends it.
- Ready-made loops (`src/services/loops`) never run by themselves: when one is due the app asks (Skip / Later / Run now), and a run is an ordinary message in the loop's own chat, under every rule above. A loop is data (a shipped prompt with the user's blanks as plain text, a schedule and limits); the model has no tool to start, change or reschedule one. Hard limits: 60 runs, 60 days, 10 loops. Only the user edits a running loop (Edit on its card; the same limits, days counted from its start, runs never below those done). Before Start a dry run shows the exact first message without sending anything. Guards that only ever hold a loop back: a phone battery guard (not met → it waits, no question) and a no-progress stop (two runs in a row with the same next steps or reply → paused, with the reason on the card; only the user resumes). A shared loop (`PA1:L:` code, `src/services/loops/loopShare.ts`) is data like a shared tool: unpacked with the same size caps (12 KB after unpacking, stopped early), only its definition is kept (name, goal and steps or prompt, schedule, limits, battery guard; never someone's runs, log or chat), built with the same hard limits (clamped), shown in full with its dry run, and installed paused and not started: it can't be run until the user presses Start on its card. The log records which tools each run's reply called (plain names only).

## 3. The HTML preview is a closed box

- There is one WebView, and it has no bridge into the app (`onMessage` is never set) and no file access. It can't navigate, open pop-ups or keep anything between previews.
- Every page starts with a CSP that blocks all network use, then a guard script that removes WebRTC (which a CSP can't block), blocks `window.open` and removes frames. Frame tags in the page text are renamed before the page is built.
- A saved `.html` file opened in another browser is outside this box.
- On the desktop (Windows / Linux app) the box is a frame instead of a WebView: the native side serves the page from its own address (`pa-preview`) with the same no-network policy plus `sandbox allow-scripts`, and the frame is sandboxed to scripts only (no origin, pop-ups, forms, downloads or storage). It gets no bridge: Tauri gives its secret call key to the app's own page only. The app window allows frames from `pa-preview` only, so a preview can't navigate itself anywhere else.

## 4. Data is never run as code

- No `eval` or `new Function` anywhere in the app, except inside the preview sandbox.
- Values are put into data, never into text that is then parsed. For example, shortcut fill-ins replace text inside a value and can't add fields.
- Each phone action builds the Android request from its own named fields. Model arguments are never passed through as they are.
- File names must match a strict pattern: no folders and no `..`.

## 5. The phone side stays small

- The app asks for a fixed list of Android permissions. Adding one means updating the test and this file.
- Only the main screen can be opened by other apps. Links from outside only fill in the chat box or offer a model download; they never send or run anything.
- Ready-made loops: "loop due" notifications use inexact alarms (no exact-alarm or boot permission) and a receiver other apps can't reach (`LoopAlarmsModule.kt`, not exported). Tapping one only opens the app, which asks Run now / Later / Skip, and only for a loop that is really due; nothing runs without that tap.
- The local API listens on the phone itself (127.0.0.1) only. It checks the Host header and a random password, compared in constant time, and accepts text only, with no tools.
- Home link, phone side (`native/homelink`, `HomeLinkModule.kt`): pairing starts only from the PC's QR code (`PA1:P:` tag; anything else is refused), the phone asks first and the PC asks its user too. The phone's tunnel to the PC listens on 127.0.0.1 only and turns away anything else; it reaches only the PC's model server, and needs that server's password. A picture asked of the PC (rule 6) comes back as at most 8 MB of PNG, saved only in the app's own cache folder. The phone's own key stays in the app's no-backup folder (never in a cloud backup). No new Android permission.

## 6. The Windows app opens doors only on purpose, and asks

The Windows app (`src-tauri`, branch `windows`) is the same app in Windows' web view. Rule: broad access, never automatic.

- The window has no internet access of its own (its content security policy). Its only frames are HTML previews from `pa-preview` (rule 3).
- Network, files, keys, previews and the model server are commands on the native side, each listed in `src-tauri/build.rs` and allowed in `src-tauri/capabilities/default.json`. Nothing else is allowed.
- Every native command runs off the window's main thread (`async`), so a slow one can't freeze the window.
- Files: the app's own folder (AppData) needs no prompt. Anywhere else, every read, write, list or delete shows an "Allow?" dialog **from the native side**, so the web screens can't skip it. `..` is refused everywhere.
- Models: the bundled llama.cpp server (pinned release, checksum checked) listens on this PC only with a random password. Running a model file from outside the app folder asks first: Allow once, Always allow this file, or Don't allow (closing the dialog is Don't allow). "Always" is only ever set by that button, and is kept in Windows Credential Manager under names the screens can't write (their key command always adds "PocketAgent:"). It covers that exact file (path, size, last-changed time): a changed or replaced file is asked about again. A model the app downloaded itself is named by its own path (`/pocketagent/…`, inside the app folder) and runs without a question; its vision part (`--mmproj`) is only ever a file the app downloaded. LoRA adapters (small .gguf style add-ons for a model) follow the same rules, stricter: one is only ever a file in the app's own folder (added through the app's own file import: the phone's file picker, or the desktop's native "Add a file" dialog, which copies it in), never a link, never from outside without that import and never a path from a paired device (a phone starting the PC's last model gets the adapter the PC user chose, nothing it names). It goes to the model server as `--lora-scaled` (strength 0–1); the server keeps running in its own folder, never in the app's data folder, because llama.cpp also loads backend DLLs from the folder it runs in. On the phone llama.rn applies it in place; one that doesn't fit leaves the plain model.
- Keys: Windows Credential Manager, never plain files. In a plain browser, saving keys is not available.
- HTML previews give the page a storage that lives only while it is open (`localStorage` / `sessionStorage` in memory; the real one throws in the no-origin preview and stopped pages' scripts). Nothing is saved or shared with the app.
- Opening things in the PC's own apps (`src-tauri/src/open.rs`, the desktop version of the phone's actions): only a web page (same check as the network door), an e-mail draft (`mailto:` with to / cc / bcc / subject / body only, never attachments; the user presses send) or a fixed list of Windows settings pages (`ms-settings:`; nothing is changed). Each asks in a native dialog showing exactly what opens; no shell: Windows' own handler (`ShellExecuteW`), on Linux `xdg-open` with the address as one argument. Calls, texts, the camera, music and other programs are not opened from the PC.
- The PC's own tools (`src-tauri/src/pc.rs`, desktop app only, each off until switched on): `pc_info` reads the hardware (read only). `run_command` shows the whole command in a native dialog **every time** (Allow / Don't allow; never "always"), with its number of lines and characters; a command with carriage returns, control characters or invisible format characters (bidi overrides, zero-width spaces, …), or more than 20 lines, is refused, so the dialog can't show something other than what runs or push a tail off the screen. It runs it in the workspace folder, stops it after 60 s and returns its output (cut). It can do anything the user can, which is why it asks each time. `open_file` opens a workspace file in its app after asking; documents, pictures, text and media only, never programs or scripts (opening those would run them).
- More PC tools (`src-tauri/src/pc_extra.rs`, desktop only): `clipboard_read` shows the clipboard's text in a native dialog before the model gets it; `media_control` presses only media keys (play / pause, next, previous, stop, volume, mute) after a native dialog; `print_file` prints a workspace document or picture after a native dialog (never programs or scripts). Screenshots are the user's "Screenshot" button (where the phone has Camera): a native dialog first, DesktopAgent hides itself while it is taken, and the picture is attached for the user to see; it reaches the model only if they send it. System notifications show text only. The quick-chat key (Ctrl+Shift+Space) only brings DesktopAgent to the front and is registered only when switched on in Settings. The tray icon opens or quits the app.
- Pictures (`src-tauri/src/image_gen.rs`, tool `image_generate`, desktop only, off until switched on): made on this PC by stable-diffusion.cpp's one-shot `sd-cli` (pinned release, checksum checked on Windows; built from the same pinned commit on Linux x64; none on ARM Linux). Never `sd-server`, which has no password: it is removed from the bundle. `sd-cli` opens no port and fetches nothing; it runs only the model files the app downloaded itself into its own folder (`Documents/image-models/<set>`, names from the model list `src/services/imageGen/imageModels.json`; the screens name a set, never a path). The picture is written to the workspace's `images` folder (the app's own folder, so no dialog); the prompt is shown in the chat as the tool call. Caps: prompt at most 1000 characters with no control or invisible characters, sizes 512 / 768 / 1024 only, at most 30 steps, one picture at a time, stopped after 10 minutes, and the chat's Stop kills it. The chat shows only pictures from that `images` folder; Save a copy is the usual native Save dialog. A small word check on the native side refuses clearly illegal prompts (sexual content involving minors) before anything runs. **It is a basic filter, not a guarantee**: it only sees words (other languages, misspellings and paraphrases get through), and the engine and models have no content filter of their own. The model list holds only models whose licence allows commercial use (FLUX.2 klein 4B: Apache-2.0; SD 1.5: OpenRAIL-M, whose use rules are shown before download); the licence note is shown the first time. A paired device can ask for a picture only as described under "Pictures for paired devices" below.
- Pictures for paired devices (link request "picture", `src-tauri/src/link.rs`; phone tool `image_generate`, `src/services/talents/PcPictureEngine.ts`): off on both sides by default. The PC's switch "Let paired devices make pictures on this PC" (kept in the credential store, out of the screens' reach) **and** that device's own "Pictures" switch in the PC's list of paired devices (off for each device, including those paired before, and again after pairing anew; switching it on asks in the PC's own native dialog, which no device can answer, and is recorded in the pairing history) must both be on, or the device is refused ("Making pictures for paired devices is off on the PC" / "This device may not make pictures on this PC; allow it on the PC"); on the phone the tool is off until switched on in Toolbox, like every tool. The device sends a prompt and, at most, sizes and steps: never a model, a path or a seed (anything else in the request is ignored); the PC uses its own first downloaded picture set and runs exactly the same checked maker as its own tool (`image_gen::make`: the same caps, the same word check, the same one-picture-at-a-time slot shared with the PC's own pictures, the same 10-minute limit). The PC shows a notification when a device starts one ("<device> is making a picture: <prompt…>"), and a copy stays in its workspace `images` folder. The answer is a JSON line, then the PNG (at most 8 MB, checked to be a PNG on both sides). If the device goes away or is removed meanwhile, its picture is stopped. The phone saves it only in its own cache folder (`pc-pictures`, a name the app makes), and the chat shows only pictures from there or the workspace `images` folder; a second PC saves it in its workspace `images` folder.
- Documents (`src-tauri/src/docs.rs`): Word, Excel, PowerPoint, OpenDocument and PDF files in the workspace are read as text on the PC (size and "zip bomb" limits; a broken PDF can't close the app). Nothing is uploaded; never files outside the app's folder.
- Files in and out (`src-tauri/src/transfer.rs`): only through the user's own choice in a native file dialog (Add a file: a copy goes into the app's folder; Save as: a copy of an app file goes where the user picks). The model can't do either.
- Network from the native side is http and https only, never the app's own internal addresses (`*.localhost`: the native bridge `ipc.localhost`, the app, previews), and never with the bridge's per-start key (`Tauri-Invoke-Key`). The page's network layer leaves those addresses alone too (`web/tauriNet.js`). Before 2026-11-09 the page sent the bridge's own Windows address through the native side, so each native call called itself until the page gave up (the 40 s Windows start); the requests that then reached the native side were for `ipc.localhost`, a name Windows does not resolve, so nothing left the PC. Both sides now refuse it, with tests.
- Publishing test builds uses the owner's own token (repository secret `RELEASE_TOKEN`: this repository only, Contents + Workflows, with an expiry), only in the "Publish pre-release" steps, which run nothing but `gh`. A test fails if it shows up anywhere else. Forks never receive it.
- Every published build comes with a `SHA256SUMS` file (a test checks each publish step). The APK is signed with our own release key from repository secrets (`ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`) in its own step only, the key written to the runner's temporary folder and removed after; without them it keeps React Native's public debug key. Windows installers are not code-signed yet.
- Keeping in step (`src/services/sync`, link request "sync"): the system prompt, memory notes, your own assistants (not their chosen model or picture) and custom tools travel between paired devices only, over the encrypted link, only when switched on **on both** (the PC's "Let paired devices keep … in step", and the device's switch for that PC); off by default. The newer edit wins item by item; empty never wins over real text; the replaced text is kept in history on that device (memory snapshots; the last 10 of the others). Times from the other device count as at most 5 minutes ahead, and what is applied is stored with this device's own time, so a clock far ahead (or a forged time) can't make an edit win forever. Your own assistants are merged one by one (each with when it last changed; matched by id, then by name): deleting one leaves a tombstone (id, name, time; the last 200, 90 days at most; malformed entries and times more than 5 minutes ahead are ignored, edit times are clamped the same way) that removes the other device's copy only if that copy hasn't changed since; the removed assistant is kept 30 days under "Recently deleted" on that device (with its picture and model choice, local storage) and can be restored; more than 5 deletions in one sync are not applied without asking. Downloaded (store) assistants are never matched, rewritten or deleted by a sync. Loops (`loopSync.ts`) are merged one by one the same way (matched by id only; tombstones of stopped loops, edit times clamped, 30 days under "Loops recently deleted", restorable, more than 5 deletions asked first), but only a loop's **definition** travels, exactly the fields a shared loop code carries (`loopShare.ts`: name, goal and steps or prompt, how often, time, run and day limits, battery guard), cleaned and held to the same hard limits as a shared code (an entry over 12 KB or one that wouldn't install is dropped): never its runs, log, chat id, next time, paused state, progress fingerprints or battery readings. A loop from another device is installed **paused and not started** (the sync result says "2 loops from the PC; start them under Toolbox → Loops"), so nothing runs on two devices unless the user presses Start on each; a changed definition updates a loop here and keeps its own runs, chat and schedule state (a running loop stays running with the new definition, as after Edit; one whose new limits no longer fit what ran here is set back to not started). A device with 10 loops takes no more (and says so). Toolbox switches are **not** kept in step: a loop's run uses the Toolbox of the device it runs on, and each device asks for its own actions. Custom tools arrive through the same checks as a saved tool and stay off until switched on on that device (Toolbox): a tool the sync adds, changes or removes is switched off before the new list is saved, and deleting a tool always switches its name off. Every change to the Toolbox switches runs one at a time and changes only the names switched (against the list as stored then), so a Toolbox left open during a sync can't write its older list back and turn a synced tool on again; an open Toolbox reloads when the switches change. On the PC, "Kept in step" notices show one at a time (later ones together after). Each side is size-capped (4 MB). A paired device can change this PC's system prompt and memory this way, which is why it is a separate switch and the PC says when something changed.
- Mirrored chats (`src/services/sync/chatSync.ts`, `chatDeletes.ts`): chats travel only when mirroring is switched on on both (separate from keeping in step, as chats are more private), with keeping in step on too, over the same encrypted link and size cap. Only newer or missing chats move; chats keep their ids; times count as at most 5 minutes ahead. Pictures stay on the device they were taken on: a mirrored message keeps only known fields and known metadata (text, the reply's steps as text, timings and similar), never picture paths, audio files, an author id or anything naming a file; only messages from the user, the assistant or a summary, of the kinds the app saves, are taken. A copy that drops or changes messages a device has keeps that device's earlier version 30 days under "Recently deleted" (restorable; with no room for it the copy is not taken). When sending to a model server the app never passes on a web address as a picture and reads only pictures in its own folder. Deleting a chat travels as a tombstone (chat id and time only; the last 500, 90 days at most; malformed ids and times more than 5 minutes ahead are ignored): it removes the other device's copy only if that copy has not changed since (a newer edit wins). A chat removed because of another device's deletion is kept 30 days under "Recently deleted" on that device (full copy, local storage, its own size room; a chat that doesn't fit isn't removed) and can be restored; more than 20 deletions in one sync are not applied without asking; the sync result says how many were deleted.
- The PC asks, a device can answer (`src-tauri/src/remote_ask.rs`, `approval.rs`, link requests "questions" and "answer"): only while switched on **on both** (the PC's switch is off at every start until the saved choice turns it on). A paired device sees the PC's "Allow?" questions word for word (direction and invisible characters shown as markers such as ⟦U+202E⟧) and can answer yes or no to one question by its id, within 2 minutes; a question too long to show whole shows its start and end (never cut at the end) and can only be refused on the device; the first answer (device or PC) wins; a device's yes is always "allow once", never "always"; pairing a new device is asked on the PC only. Only the devices allowed one by one on the PC ("May answer" in its list of paired devices; off for each device, including those paired before this choice existed, and again after pairing anew) get the questions or may answer; any other paired device is refused ("This device may not answer this PC's questions; allow it on the PC"). Allowing a device is asked in the PC's own native dialog, which no device can answer, and is recorded in the pairing history the paired devices see; stopping it asks nothing. Each device answer is logged on the PC (`link/answers.log`: the device's name, its answer and the whole question on one line, escaped, up to 4000 characters), in a folder the screens' file commands can't reach without asking (the settings folder on Linux, local AppData on Windows). When a device answers, the PC user gets a notification at once ("<device> allowed: …"); the PC's own dialog can't be closed from the native side, so whatever is pressed there afterwards changes nothing and a note says "This was already answered on <device>". This means a paired device can allow what the PC would ask about, which is why it is its own switch, off by default.
- PC to PC (`src-tauri/src/link_client.rs`): a second PC can be the other end of a home link, with the phone's own link library unchanged (its own key, 127.0.0.1 only, the PC's one-time code only). Its key is kept like the PC's link key, out of the screens' file space (Windows Credential Manager; on Linux an owner-only file in the settings folder); a key file from before 2026-11-15 is moved there, so pairing is kept. The phone's key file is owner-only (0600). The code is pasted instead of scanned ("Copy the code" on the main PC); the main PC still asks before pairing, and the second PC is listed and removable there like a phone.
- Home link ("Use this PC's model from your phone", `src-tauri/src/link.rs`): off until the user switches it on. Devices dial each other by public key (iroh); the connection is encrypted from the PC to the phone, and a relay (used when no direct path is found) passes it on without being able to read it. Pairing: a QR code with the PC's key and a one-time code (10 minutes, one try), then a native "Pair with the phone …?" dialog; only then is the phone's key saved. The model server's password is passed by environment (`LLAMA_API_KEY`), never on its command line (which any program on the PC can read). Through the link, every request is one stream, read whole and checked before anything reaches the model server: it must be one of the model server's own requests (health, props, models, chat / completions) with the model's current password, with a plain `Content-Length` body (no `Transfer-Encoding`, at most 16 MB, no folded or broken headers) and nothing after it (a second, pipelined request is refused); the model server gets it with `Connection: close`, so it answers once and closes, and the phone closes its local connection then, so the next request is checked the same way. Anything else gets 403, so another app on the phone that finds the phone's local port gets nothing, and `/slots` and other endpoints can't be reached by riding along. In chat and completion requests, pictures, sound and video must be inline (`data:`): an address (`http://…`) is refused, because the model server would fetch it from inside the PC's home network. The model server runs with `--no-slots` (its `/slots` would hand out the last conversation), and `/metrics`, `POST /props` and slot saving stay off. A paired phone can do exactly three things on its own (plus answering this PC's questions and asking for pictures, each only while allowed for that device, above): ask whether a model is running, start the model this PC last ran (the PC picks it, the phone names nothing; never one that would need an "Allow?" on the PC: a file outside the app folder that isn't "always allowed" is refused, since nobody may be at the PC), and pass HTTP requests to this PC's own model server on 127.0.0.1. Nothing else is reachable (no files, tools or other ports). Paired phones and the link key live in the credential store under names the screens can't write. Remove a phone and it is shut out at once: its open connections (a model request, a sync) are closed, and for an hour it can't ask to pair again. A device that is already paired or was removed lately can't use up a pairing code (only a wrong code from a new device does). A device must send its request line within 10 seconds, and runs one sync at a time. Pairing history: every code made, phone paired and phone removed is recorded on the PC and sent to the paired phones with each status, so a code made while you're away shows up on your phone ("Pairing activity on your PC").
- Downloads (models) stream straight to disk through the native side: http/https only, the app's own folder needs no prompt, anywhere else asks; a half-finished download stays a `.part` file and never looks like a model.
- The desktop app makes no network calls at start-up (the phone's device-rules fetch from PocketPal's CDN is off on the desktop).
- Tauri's script nonces stay on; its style nonces are off (`dangerousDisableAssetCspModification: ["style-src"]`), because the app's styles are added at run time. Styles can't run code, and the policy stops them loading anything from outside.

## 7. No outside connection the user didn't ask for

Audit 2026-11-09 (every outside address in the code, plus the desktop app's actual traffic in its first minute: none). Phone app audited again in the code 2026-11-15 (every `fetch`, `axios`, `XMLHttpRequest`, WebSocket and native download); the list below is what it found. Its real traffic on a phone is still to be watched once (TODO.md, Pre-release).

- Nothing contacts an outside service on its own: no reports, no analytics, no crash reporting, no Google. `src/config/outside.ts` keeps PocketPal's original senders in the code but off: feedback, content reports, model error reports and shared benchmarks (PocketPal's Firebase / Google App Check, after a google.com probe) are refused before any connection (the error report is copied instead); the device-rules download from cdn.jsdelivr.net at every phone start is off (built-in rules are used). A test pins both off.
- Not built in on Android: Firebase (no project; its JS modules unlinked, its Android libraries commented out), Google Sign-In and Google Play billing (unlinked in `react-native.config.js` since 2026-11-15, so Google's billing library is not in the APK; their JavaScript is replaced by stand-ins that say "not available", `stubs/android`; a test pins it). The PalsHub account code stays but never starts (it needs a Supabase address, which PocketAgent builds don't have; purchases are off: `NO_PURCHASES`).
- New outside connections need this file updated and their switch or consent; reviewed in the security audit before release.

**Every outside address the phone app can contact** (nothing else is in the code):

| When | Address | Switch |
|---|---|---|
| At start-up, with nothing set up | none | — |
| At start-up and when the app comes back to the front (at most once a minute): the model list of each server **you added** | that server's own address (a cloud provider such as api.openai.com, api.anthropic.com, generativelanguage.googleapis.com, api.groq.com, api.deepseek.com, openrouter.ai, or your own server) | remove the server |
| Same, for a paired Home PC | the home link: number0's iroh relay and discovery servers, then your PC (encrypted; they see which keys connect, never the content) | remove the Home PC server, or switch off "Use this PC's model from your phone" on the PC |
| While the app is open, if "Show this PC's Allow? questions here" is on: every 8 s (60 s when the PC is away) | the home link, as above | that switch (off by default) |
| Keeping in step / mirrored chats, if switched on on both | the home link, as above | those switches (off by default) |
| Asking the Home PC for a picture (tool `image_generate`), when switched on and the model uses it | the home link, as above | the tool's Toolbox switch, and the PC's picture switches (all off by default) |
| Chatting with a cloud model or server you added | that server | — (you chose it) |
| Opening model search, a model's details, or downloading a model, voice model (Whisper) or speech voice | huggingface.co (and the file host it redirects to) | — (you asked); a Hugging Face token only if you added one, and only to huggingface.co |
| Opening the Models screen with a downloaded Hugging Face model whose checksum isn't stored yet (older downloads) | huggingface.co, once per model, to fetch its SHA-256 | — |
| Web search / read a page tools, when switched on and the model uses them | DuckDuckGo (html.duckduckgo.com) or the search service you set up (Brave, Tavily, Exa, Firecrawl, Parallel), and the page being read | the tool's Toolbox switch (off by default) |

Not the app's own traffic: Android itself (system updates, the Play Store, the keyboard, the system's speech voice if you pick it) and apps opened by phone actions. A link from another app only fills the chat box or offers a model download; it never connects by itself (rule 5).

The desktop app makes no network calls at start-up (rule 6); its outside connections are the same kinds as the phone's (servers you added, model downloads, search tools, the home link).

## For mods (planned)

A mod is data, never code. It lists every tool it uses, its full contents are shown before install, and it installs switched off. It goes through the same checks as a tool the model saves (rule 2).
